## Consistency rules

- Seat counts changed only via atomic `$inc` with conditions, inside a transaction when promoting.
- Append-only: EntryVersion, AuditLog, Submission (verdict fields may be updated, code never).
- Standings and progress are derived data, recomputed from Submission rows; never trusted from client.
- Hidden test data lives only in TestCase; Submission stores code and verdict only (no judge stdout of hidden tests).

## Implementation notes (as built)

- **No partial indexes and no transactions**: uniqueness uses synthetic keys (`subjectKey`) that are rewritten when a record is cancelled; capacity uses the `Seat` collection. Works on a standalone MongoDB and on emulators.
- Models implemented: User, RefreshToken, Venue, Event, Activity, Registration, Seat, Team, TeamMember, Invitation, Notification, Announcement, Availability, Shift, ShiftAssignment, Task, ReplacementRequest, CheckInToken, CheckIn, Issue, Rubric, Entry, EntryVersion, JudgeAssignment, Score, Result, AuditLog, Problem, TestCase, Contest, ContestRegistration, Submission, Editorial (see `apps/server/src/models/index.ts`).
- `TestCase.input/expectedOutput` and `Submission.code` are `select:false`; code that needs them must call `.select('+field')` explicitly (only the judge service and setter endpoints do).
- `Result` (draft/official), `EntryVersion` and `AuditLog` are append-only by API design (no update/delete route).
